# 项目链路逐字稿（约 4 分钟，照着念即可）

我这个项目叫「数据开发助手」，做的是 Text-to-SQL 加指标口径问答。我本身是做数据开发的，所以特意选了一个能用 SQL 执行结果当硬指标的方向——评测不靠人工打分，直接看结果集对不对。下面我按一条请求从进来到回流的顺序讲一遍。

## ① 问题

用户在 SQL 工作台里输一个自然语言问题，比如「2024 年 3 月各品类的 GMV 是多少」，请求打到 FastAPI 的 `/sql`。如果问的是「净支付额和 GMV 什么区别」这种口径问题，就走 `/rag`。

## ② 拼 Prompt

`/sql` 这边我不手写表结构提示词，而是让 `common/schema.py` 的 `build_input()` 直接读 `data/warehouse_schema.sql` 这份 DDL，拼成三段：表结构、可选的业务口径上下文、最后是问题。这样 Prompt 和真实 DDL 不会漂移。

口径问答走 RAG：`rag/ingest.py` 把数据字典切块、向量化建索引，`retriever.py` 检索 top-k 片段，拼成带 `[1] [2]` 来源标注的 context 塞进 Prompt，再由模型生成带引用的回答，instruction 里明确要求「资料没写的内容不要编造」。我对 RAG 的判断标准很明确：只把文档列表返回给用户不叫 RAG，必须把检索内容塞进 Prompt 让模型生成答案才算。另外训练、评测、线上三处的 Prompt 全部走同一个 `build_input()`，因为 Prompt 不一致是 Text-to-SQL 微调最常见的隐性掉分原因。

## ③ 生成 SQL

生成器统一抽象成 `common/generator.py` 的 `generate()`：system 里是固定 instruction，要求只输出 SQL、不要解释、不要 markdown 代码块；user 里是刚拼好的 input。模型输出过一道 `strip_sql()`，去掉代码围栏、去掉「SQL:」前缀、按分号取第一条语句，保证后面能直接丢进数据库执行。

现阶段联调走 OpenAI 兼容 API；正式实验时只要把生成器换成基座、`local` 加载 LoRA adapter、或者 `vllm`，评测逻辑一行都不用改。这么设计就是为了保证基座、v1、v2 三组的对比是公平的。

## ④ 执行

线上 `/sql` 带 `execute=true` 时，用 sqlite3 连到我用固定随机种子生成的测试数仓执行，返回 `rows` 和 `columns`；这一步只用于本地调试，生产必须关掉，避免任意 SQL 执行。评测里更严格：gold SQL 和预测 SQL 在同一个库分别执行，各取最多 1000 行。

## ⑤ 结果集比对

评测脚本是 `eval/run_eval.py`。开跑前先 `verify_frozen()`：拿 `data/eval.jsonl` 的实际 sha256 和 `eval.jsonl.sha256` 里记录的比对，不一致直接报错退出——评测集一旦被改动，所有对比数字作废。然后逐条生成、执行、比对：`result_equal()` 默认按无序多重集比，浮点数统一保留 6 位，加 `--ordered` 才严格卡行顺序；另外单独算 `exact_match`，也就是 SQL 归一化后字面是否一致。

主指标我用的是 `result_accuracy` 而不是 `exact_match`，因为同一个结果可以有很多种 SQL 写法，字面一致不该当硬标准；辅助看 `execution_success`。还有一条硬规矩：`debug_gold` 生成器只用来验证评测管道通不通，结果打 `official=false`，默认排除在对比表外，绝不拿它产数字。

## ⑥ 错误归因

结果不对的样本进 `eval/error_taxonomy.py`，做 6 类自动归因，全是可复查的启发式规则，不依赖人工打分或者 LLM-as-judge。执行报错先看是不是 `no such column` 这类 schema 对象用错，是就归 `SCHEMA_ERROR`，否则 `EXEC_ERROR`；能执行但结果不对就比结构：gold 有 DISTINCT 预测没有，归 `DEDUP_ERROR`；缺 GROUP BY、JOIN 数或聚合数、窗口函数不一致，归 `JOIN_AGG_ERROR`；结构完全一样、只是时间窗口或阈值字面量不同，归 `TIME_SCOPE_ERROR`；剩下归 `OTHER_RESULT_ERROR`。每条都留下 gold SQL、预测 SQL、结果集行数和归因说明，能归档能复查。

## ⑦ 回流修数据

这一步我认为最值钱。归因不是为了写报告，是为了回流修数据：哪类错占比高，就定向补哪类样本——时间口径错得多就补时间窗口和分区裁剪，去重错得多就补 DISTINCT 场景。新样本回到流水线：`clean.py` 跑 8 条质检规则，必填字段缺失、非查询语句、SQL 不可执行、未替换占位符这四条是 error 级直接丢弃，事实表没做分区裁剪、问题夹带答案 SQL、问题与 SQL 结构不一致、样本超长这四条是 warn 级保留但标记；然后 `dedup.py` 做 SQL 归一化后的精确哈希加 MinHash 近似去重，`sample.py` 按难度、业务主题和 SQL 模板分桶做分层均衡采样，`build_sft.py` 生成训练集，并且和评测集再做一次精确加近似的泄漏检查。修完数据再训一轮，用同一个冻结评测集复测，看那类错误的占比有没有降下来。

整个闭环就是：数据决定表现，评测暴露问题，归因定位到数据，修数据再验证。

## 收尾

所以定位我说得很清楚：这不是从零预训练、也不是造基座，是基于 7B 开源基座做 LoRA-SFT 的 post-training，把现成模型调成能按我们数仓口径产出 SQL；企业私有的表结构和指标口径交给 RAG 补，微调只改行为和输出格式。目前代码骨架和端到端联调已经跑通，正式的基座、v1、v2 三组实验和前后对比表，按计划用 12 月底冻结的 200 条评测集在 1 月到 2 月初完成。
