## 接入方式

把下载后的数据整理成 `data/raw/<name>.jsonl`，字段见 `data/SCHEMA.md`。
`pipeline/clean.py` 会自动识别 Spider 风格字段（`query` → `sql`）并统一 schema。

## 注意

- **评测集只用自建种子样本 + 本项目独立标注**，不与公开训练语料混用，避免数据泄漏争议。
- 公开数据集的 schema 与本项目 `warehouse.db` 不一致时，gold SQL 无法在测试库执行，会被 `clean.py` 的「可执行性校验」丢弃；保留其 `question` 用于数据增强需另行改写 SQL。
- 12/31 冻结评测集后，新增语料只能通过 `build_sft.py --force` 重新分层，不要手工往 `eval.jsonl` 里加。

## 2026-11-07 扩充语料说明

`scripts/gen_samples.py` 生成 274 条自写样本，设计上**按结构而非按字面量**变化：
项目用归一化哈希去重，日期/数值会被抹成 `?`，所以换日期不算新样本；
这里让差异来自表名、列名、聚合函数与子句组合，244+ 条唯一结构全部在测试库执行通过。

流水线实际结果（可复核，见 `data/processed/` 报告）：

| 步骤 | 结果 |
|---|---|
| 清洗（50 种子 + 274 扩充） | 324 → 324 条，W001 warn 10 / W003 warn 8（warn 保留） |
| 去重（归一化 SHA1 + MinHash 0.88） | 324 → 196 条（精确 1 / 近似 127） |
| 分层采样 | 196 条，覆盖 3 档难度 × 9 类主题 × 8 类模板 |
| 冻结（预冻结） | 训练集 146 条、评测集 39 条，泄漏校验移除 11 条近似重复 |

> 近似去重删掉 127 条是预期行为：同族 SQL 只换一个列名，MinHash 相似度仍超阈值。
> 这也说明**靠模板化合成撑到 1000+ 条效率很低**，必须混入真实业务样本。
> 当前 39 条评测集是预冻结的中间状态，不是 PLAN 要求的 200 条正式评测集。

## 2026-11-07 示范 SQL 已生成

20 题的 SQL 已写入 `data/raw/real_samples.jsonl`，字段为
`id / question / sql / db_id / theme / source / license / tags`（定义见 `data/SCHEMA.md`）。

覆盖 8 类主题 / 6 类 SQL 模板 / 2 档难度。

**重要：这些还不是「真实样本」**。`source` 标的是 `sample` 而不是 `real`，因为 SQL 是助手
按模拟数仓口径写的示范，不是你真实业务的口径。请逐条核对（尤其 GMV、净支付额、客单价、
复购、跨月边界的定义），改成你自己数仓的写法后把 `source` 改为 `real` 再接入。
面试里说「真实业务样本」必须名副其实。

几处口径歧义，已在 SQL 里显式选定，核对时重点看：

| 样本 | 采用的口径 |
|---|---|
| `real_001` | 周按 `dim_date.week_of_year`（周一为首）；3/1 是周五，第一周只有 3 天。要完整自然周需从 3/4 起 |
| `real_004` / `real_017` | 客单价 = 已支付订单 GMV / 已支付订单数（分母不含取消/退款单） |
| `real_013` | 「当月无成功支付」按同一 `user_id` 在 3 月内判断，跨月不算 |
| `real_020` | 日均 GMV 按当月**有订单的日期**求平均，不含零单日 |
| `real_019` | 3 月与 4 月各自独立求和，`UNION ALL` 输出两行，不算环比增长率 |

接入方式（**核对完口径再跑一次即可**，避免反复 `--force` 让冻结失去意义）：

```bash
python pipeline/clean.py
python pipeline/dedup.py
python pipeline/sample.py --target 1200
python pipeline/build_sft.py --eval-size 200 --force
```

`clean.py` 会自动读取 `data/raw/*.jsonl`，所以文件放进去就会被纳入。
`--force` 会让此前所有对比数字作废（当前还没有正式数字，所以现在重建是安全的）。
